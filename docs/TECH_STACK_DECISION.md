# 技术栈决策

## 1. 第一版推荐技术栈

| 层级 | 推荐技术 | 用途 | 决策 |
| --- | --- | --- | --- |
| 语言 | TypeScript | 统一编辑器、schema、渲染器类型 | 采用 |
| 编辑器 UI | React | 本地可视化编辑器、HUD 预览组件 | 采用 |
| 构建工具 | Vite | 本地开发服务和前端构建 | 采用 |
| 视频渲染 | Remotion | 基于 React 组件渲染 MP4 | 采用 |
| 配置校验 | Zod | 校验课程配置和时间轴事件 | 采用 |
| 数据存储 | 本地 JSON | 保存项目配置 | 采用 |
| 脚本运行 | Node scripts | 保存、校验、渲染命令入口 | 采用 |
| 样式 | CSS Modules 或普通 CSS + tokens | 实现固定 HUD 视觉系统 | 采用 |

## 2. React

### 2.1 使用原因

React 适合第一版，因为：

1. 编辑器需要组件化 UI。
2. 最终视频 HUD 也可拆成组件。
3. Remotion 原生使用 React 组件表达视频画面。
4. 编辑器预览和渲染器可以复用 HUD 展示组件。
5. 模块点选、属性面板、时间轴表格都适合用 React 状态管理。

### 2.2 使用边界

React 用于：

1. 本地编辑器界面。
2. 最终视频 HUD 组件。
3. Remotion Composition。

React 不用于：

1. 实现课程平台。
2. 实现网页播放器产品。
3. 实现自由画布设计器。

## 3. TypeScript

### 3.1 使用原因

第一版必须采用 TypeScript，因为配置和事件模型是产品核心：

1. 课程配置字段多，需要类型约束。
2. 时间轴事件需要枚举和 payload 类型。
3. 编辑器和渲染器应共享类型。
4. 后续 Agent 能更安全地扩展模型。
5. TypeScript 与 Zod 可互相配合，减少配置漂移。

### 3.2 关键要求

1. 所有核心模型定义在 `src/schemas` 或相邻类型文件中。
2. 不允许编辑器和渲染器各自定义一套不一致的数据结构。
3. `TimelineEvent.type`、`targetComponent`、`layout.displayMode` 等字段必须使用枚举或联合类型。

## 4. Remotion

### 4.1 使用原因

Remotion 是第一版最适合的渲染方案：

1. 可以用 React 组件描述最终视频画面。
2. 可以逐帧读取当前帧和 FPS。
3. 适合把配置转成可重复渲染的视频输出。
4. 对 1920 x 1080 MP4 输出支持成熟。
5. 编辑器 HUD 预览组件可以与渲染组件共享语义。

### 4.2 使用边界

Remotion 用于：

1. 渲染主视频。
2. 渲染讲师视频或头像。
3. 渲染 TopHeader、ChapterMap、TaskTracker、WarningPanel、CourseStageBar、BottomStatusHud 等 HUD。
4. 根据时间轴事件生成帧级状态。
5. 输出 MP4。

Remotion 不用于：

1. 编辑器播放器控件。
2. 用户登录和数据管理。
3. 云端队列。
4. OBS 实时叠加。

## 5. Vite

### 5.1 使用原因

Vite 适合作为第一版本地编辑器开发工具：

1. 启动快。
2. React 支持成熟。
3. 配置简单。
4. 适合本地 Web 工具。
5. 与 TypeScript、CSS、静态资源开发体验良好。

### 5.2 工程定位

Vite 负责编辑器开发和本地预览，不负责最终 MP4 渲染。最终视频输出由 Remotion 和 Node scripts 触发。

## 6. Zod

### 6.1 使用原因

课程配置必须可校验，否则渲染失败会很难定位。Zod 用于：

1. 校验 `lesson.config.json`。
2. 校验时间轴事件字段。
3. 校验素材引用是否符合格式。
4. 给编辑器提供字段级错误。
5. 给渲染前检查提供阻断项。

### 6.2 校验层级

第一版建议分为三层：

1. Schema 校验：字段类型、必填、枚举值。
2. 业务校验：阶段时间顺序、事件持续时间、关联 ID 是否存在。
3. 渲染校验：素材路径是否存在、输出目录是否可写、主视频是否可读取。

## 7. 本地 JSON

### 7.1 使用原因

第一版推荐使用本地 JSON 保存项目配置：

1. 与“本地可视化编辑器”目标一致。
2. 不需要数据库和账号。
3. 方便高级用户查看、复制、备份和复用。
4. 方便 Remotion 渲染脚本直接读取。
5. 降低 MVP 工程复杂度。

### 7.2 建议文件

推荐默认配置文件：

```text
src/data/lesson.sample.json
public/input/lesson.config.json
```

实际开发时可选择一个主入口，但必须保证编辑器保存和渲染器读取的是同一结构。

## 8. Node Scripts

### 8.1 使用原因

Node scripts 适合承担本地工程操作：

1. 校验配置。
2. 启动 Remotion 渲染。
3. 检查素材路径。
4. 输出 MP4 到 `out`。
5. 后续支持批量渲染。

### 8.2 建议脚本

```text
scripts/validate-config.ts
scripts/render-lesson.ts
scripts/check-assets.ts
```

第一版脚本只作为工程入口，不承担复杂业务状态。

## 9. 为什么第一版不做数据库

第一版不做数据库，原因：

1. MVP 目标是验证时间轴 HUD 渲染价值，不是验证数据平台。
2. 本地 JSON 已能满足单项目编辑、保存、导入和渲染。
3. 数据库会引入迁移、同步、备份和部署成本。
4. 没有登录和协作时，数据库收益有限。
5. 配置文件更利于后续 Agent 调试。

## 10. 为什么第一版不做登录

第一版不做登录，原因：

1. 产品不是课程平台。
2. 第一版以本地工具为主，不需要身份系统。
3. 登录会引入账号、安全、会话、权限和隐私问题。
4. 核心路径是导入素材、配置时间轴、导出 MP4。

## 11. 为什么第一版不做云端 SaaS

第一版不做云端 SaaS，原因：

1. 云端渲染会引入上传大视频、存储、队列、费用和失败恢复问题。
2. MVP 阶段本地渲染更可控。
3. 当前产品约束要求本地可视化编辑器。
4. 云端化不影响时间轴模型和渲染模型验证，可后置。

## 12. 为什么第一版不做 Electron

第一版不做 Electron，原因：

1. Vite 本地 Web 编辑器已能支撑核心验证。
2. Electron 会增加打包、自动更新、跨平台文件权限和体积成本。
3. 当前阶段更需要先稳定配置模型和渲染管线。
4. 后续如果需要桌面分发，可以在 Web 编辑器稳定后再包壳。

## 13. 为什么第一版不做 OBS 插件

第一版不做 OBS 插件，原因：

1. 产品输出是渲染后的 MP4，不是直播实时叠加。
2. OBS 插件偏实时场景，与课程后期包装目标不同。
3. 时间轴事件以主视频时间为基准，适合离线渲染。
4. OBS 会引入实时同步、场景源管理和插件分发复杂度。

## 14. 为什么第一版不做 Premiere 插件

第一版不做 Premiere 插件，原因：

1. 产品核心是配置驱动的课程 HUD 渲染器，不是传统剪辑软件插件。
2. Premiere 插件会引入宿主软件依赖、插件分发、版本兼容和时间线 API 复杂度。
3. 第一版目标用户需要低门槛本地可视化编辑器，不应要求用户安装或理解专业剪辑软件。
4. Remotion 离线渲染更适合复用同一套 React HUD 组件和 JSON 配置。
5. 后续如需接入剪辑软件，应在核心配置模型和渲染管线稳定后单独设计。

## 15. 最终决策

第一版采用：

> React + TypeScript + Vite + Remotion + Zod + 本地 JSON + Node scripts。

该技术栈与产品的核心定位一致：本地配置、可视化预览、时间轴驱动、稳定渲染 16:9 MP4。
